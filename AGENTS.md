# Working on Home Library

The one deep guide to this repo, for agents and developers alike: read it before any change. The rules every project shares are shared-tooling's standards, indexed in [shared/standards/README.md](shared/standards/README.md); what is here is Home Library's own, and the last two sections list where it departs from them, each with its reason, and what it hasn't brought up to them yet.

Never run `git commit`, `git tag`, `git push`, or create a repository without the owner's explicit permission for that specific action in the conversation. Prepare changes and wait. A release is the commit CI tags when a push to `main` raises `web/package.json`'s version, deployed with `task deploy`; `task deploy -- -Preview` ships the working tree as it is, to try a build on the droplet before it is committed.

Read PLAN.md before changing anything structural. It holds the product decisions, the data model, and the phase order. A change to any of them updates PLAN.md in the same change, with a dated line in docs/decisions.md.

## Where things are

- `cmd/homelibrary`: the one binary and its subcommands: `serve`, `read-text` (the text service), `migrate`, `backup`, `setup-code`, `import`, `openapi`, `dev-session` and `version`.
- `internal/`: packages by domain. Handlers in `internal/server` and `internal/api` stay thin; the rules live in `internal/catalog` and `internal/lookup`, and sign-in's in `internal/auth`. `internal/db` is sqlc's output beside the hand-written open, search and migration code, with the queries in `internal/db/queries`, the goose migrations in `internal/db/migrations`, and `schema.sql`, what they build; `internal/db/dbtest` gives each test a migrated database of its own. `internal/civil` is the calendar day (`civil.Date`).
- `web/`: the Vue app, embedded in the binary by `web/embed.go`, with its unit tests in `src/__tests__/` (`*.spec.ts`) and its end-to-end suite in `web/e2e`. Under `web/src/`: route pages in `views/`, components in `components/`, each `useX` in `composables/useX.ts`, the Pinia stores (`library`, `session`, `units`) in `stores/`, the router in `router/index.ts`, the API's type names in `types/index.ts` (imported from `@/types`, never from the client), the fixed option lists in `constants/index.ts` (their words in `app/format.ts`), and the client, the committed spec and its generated types in `api/`. `app/` keeps the app-wide pieces: formatters, error handling, the theme, scheme and CSP, the Stacks' arrangements, the ISBN, citation and detection helpers, the forms' shapes, navigation, the offline catalog and the clipboard.
- `deploy/`: the templates of the systemd units and the Apache vhost, which the deploy fills from the git-ignored deploy config and installs where they differ. The nightly backup's units are written by the deploy itself (shared-tooling's `Install-BackupTimer`).
- `scripts/`: `deploy.ps1` (`task deploy`; `Get-Help .\scripts\deploy.ps1 -Full` gives its whole run) and `pull-backup.ps1`, the daily copy of the droplet's backup to this machine, both on shared-tooling's SharedDeploy module.
- `docs/ops.md`: the host, releasing, the deploy, the backups and how to restore them. `docs/decisions.md`: a dated line for each decision. `CHANGELOG.md`: what each release changes, its section the release's notes.
- The app's one version is `web/package.json`'s. A push to `main` that raises it is tagged `v<version>` by CI's `release` job once every other job passes (`.github/scripts/release.sh`), and the binary reports that tag (`/healthz`, through the build's ldflags).
- `shared/`: the shared-tooling submodule, at the release its `VERSION` names. It moves only with `task shared:update -- vX.Y.Z`.

## Principles

- Other projects in `C:\Web Projects` (Kindred Nights above all) are references for tooling and host mechanics. Nothing is copied for being there; what every project shares comes from `shared/`.
- One way to do each thing: one API client, one form pattern, one cover component, one table. A second way is a refactor of the first.
- Endpoints are resource-shaped. Nothing is disabled or kept for later; dead code goes in the change that makes it dead.
- A lookup fills blanks. It never overwrites a field the owner typed or an import brought; what a source gives otherwise is offered, and taken only when the owner says.

## Go

- Stdlib first. Packages by domain. Handlers stay thin; rules live in `internal/catalog` and `internal/lookup`, and sign-in's in `internal/auth`.
- Signing in and out, setting a device up with a code, and making a passkey are API operations (`/auth/*`, `/passkeys`), working on the session their context carries: the server wraps the mux in scs's `LoadAndSave`, and its host check puts the request's configured origin in the context (`api.WithRequest`) for the passkey's relying party. Only a share link's `/s/{token}` and the calendar feed answer outside the API, being addresses already given out.
- All SQL through sqlc, but for the FTS5 statements sqlc cannot parse (the search and the index's writes, in `internal/db/search.go`) and the backup's `VACUUM INTO` (see docs/decisions.md). A query names the columns it reads, never `*`. sqlc reads `internal/db/schema.sql`, which `TestSchema` writes from what the migrations build (`task gen`) and fails on when it differs.
- Migrations are append-only, and each sets `PRAGMA user_version` to its own number, which a test holds to goose's version. A table rebuild follows database.md's steps in a `-- +goose NO TRANSACTION` file, as 00038 does; `db.Migrate` rolls a failed one back and turns foreign keys on again.
- Errors wrapped with context, logs through `slog`. No package-level variable holds state, config included: what a package needs is built in `main` and passed in, in structs. Constants, sentinel errors, fixed lookup tables, compiled patterns and the build's version (set by the linker) are not state; `dbtest`'s template, built once per test binary, is the one exception. Environment variables are prefixed `HL_`.
- Each operation's description opens with its guard in the standard's terms, from the helper that made it: `Guard: admin.` (`op`, the owner alone), `Guard: auth.` (`readOp`, anyone signed in, the owner or a share link's visitor) or `Guard: public.` (neither, the sign-in operations and the session check). The API document's description says what each means, and a test holds every one.
- The server's log level is a `slog.LevelVar`, set from `HL_LOG_LEVEL` at start and changed by the owner on Settings (`PUT /log-level`) until the next restart.
- Cache headers (`internal/server/cache.go`): an API `GET`, or `/healthz`, that nobody signed in to and that answers 200 is a public read, sent `no-cache`; a list the browser receives whole (every `list-*` operation, marked by `op` and `readOp`) is `private, no-cache` (`api.KeptList`), kept in the browser's own cache alone and asked for again each time. Both carry a strong `ETag` and are answered 304 when `If-None-Match` matches. Every other API answer, a list's error included, is `private, no-store`, and streams through unheld. A sign-in that ends (signed out, its passkey or share link gone) sends `Clear-Site-Data: "cache"`, so the kept lists go with it. Two differ from the baseline, which lets a project say how and why here: a kept list is `private, no-cache` where the baseline has `private, no-store`, so that an unchanged list costs an empty 304 as performance.md asks, while the browser still checks before every use; and a cover is `private, max-age=31536000, immutable`, since its address is a random name that changes with the file, so a kept copy is never stale, and a library page shows hundreds. The front end's content-hashed files are `public, max-age=31536000, immutable`, its shell `no-cache`, and the install icons `public, max-age=86400`, since they change only with a release and a day late is harmless.
- A form's save can't undo a change made since the form read the record: every record a form saves whole carries `updatedAt` (`catalog.Stamp`, embedded in its input, so its answer has it too), the form sends back the one it read, and the save checks it in its own transaction (`catalog.Unmoved`), refusing a moved record with 409 and its error at `body.updatedAt` (`MovedError`); a save that sends none isn't checked. Every write to a field a form saves moves the stamp to now, or a second past the last if that is later, so two saves in one second still differ: a series renamed moves its works', and a shelf taken by another area moves the area's that had it. A book's stamp is the later of its work's and its edition's.
- The `http.Server` sets `ReadHeaderTimeout`, `ReadTimeout` and `IdleTimeout`, and no `WriteTimeout`, which would cut the change feed; an upload sets a longer `BodyReadTimeout` of its own (`uploadReadTimeout`).

## UI and accessibility

- WCAG 2.2 AAA is the target, in the light scheme and the dark one alike. A shortfall that cannot be helped is a dated line in docs/decisions.md, never a silent one.
- Contrast: 7:1 for text, 4.5:1 for large text (24px, or 19px bold), 3:1 for control boundaries, focus rings, and meaningful icons. `src/__tests__/app/theme/contrast.spec.ts` computes every pair from the preset; a new color pair is added there.
- Colors only through tokens in `web/src/app/theme/`; `npm run lint` fails on a literal color anywhere else. Token names say what they are for (`ink-muted`, `hairline`), never what they look like.
- Light and dark follow the device, or the owner's choice on it in Settings, and are equals: every page is checked in both. The scheme is one class on the page's root (`scheme-dark`), set only by `app/scheme.ts`; nothing styles by `prefers-color-scheme` itself.
- Every control is at least 44 by 44 CSS pixels, with a pointer or a finger. Focus is always visible. Each animation and transition honours `prefers-reduced-motion` in its own rule; there is no global switch.
- Prose (descriptions, notes, help) is at most 70 characters wide with line height 1.5 or more, never justified.
- A skip link leads every page in the app's frame, to `<main id="main-content" tabindex="-1">`, moving focus without a hash in the address, and after every move to another page the focus goes to that `main` unless the page focused a field of its own; one `h1` a page, headings in order; landmarks for the bar, the navigation, and the main content. The pages before signing in are a main alone, with nothing to skip.
- A link standing on its own, not in a sentence, takes `link-target` (a table row's, `row-link`) for its 44-pixel reach. A link inside a sentence is underlined (`underline`), since its color alone is not enough beside muted text (axe's `link-in-text-block`).
- Errors say what happened and what to do; a destructive action asks first and says what it removes.
- Check every page at 390px and at 1280px, in both schemes, with its dialogs open, before calling it done.

## Data

- SQLite: WAL, foreign keys on, busy timeout 5000, synchronous NORMAL; one write connection, a read pool; multi-statement writes in a transaction.
- A timestamp is `DATETIME`, RFC 3339 in UTC to the second (`2026-11-07T09:18:09Z`), with `CHECK (col IS strftime('%Y-%m-%dT%H:%M:%SZ', col))`, mostly written by its `strftime('%Y-%m-%dT%H:%M:%SZ', 'now')` default; Go writes one as `t.UTC().Format(time.RFC3339)` and reads it as its text (sqlc's override; `sql.NullString` where it may be unset). A day is `DATE` with `CHECK (col IS date(col))`, read and written as `civil.Date`, whose empty value is `NULL`. A date or time not set is `NULL`, never `''`; the API still sends a day not set as `""`. Sessions are the app's own store (`internal/auth/sessions.go`), each under its token's hash with a `DATETIME` expiry, and goose's `goose_db_version` takes the same timestamp form (00039). Every table a form saves has `updated_at` (00040 gave it to borrowers, loans, share links, areas, bookcases and shelves). Money is integer cents. Dimensions are integer millimetres.
- The app never makes a database: `db.Open` refuses a missing file, so a new one (devdata's, a test's) is an empty file, then migrated.

## Checks

- `task check` passes before a change is done: at once, `task lint` (Go vet, the shared golangci-lint config, the front end's ESLint, Stylelint, token check, types and Prettier, the scripts, and the vulnerability audits), `shared:docs:check` (Markdown, the shared repo files and workflow refs, the CHANGELOG's links), the specs' types (`web:specs`), `task test:coverage` (Go and Vitest, each held to its floor) and the OSV scan; then `task test:e2e`, and `gen:check`, which fails when the committed schema, sqlc's code, `openapi.json` or `schema.d.ts` differ from what the generators make. CI runs the same through shared-tooling's workflows.
- The lint configs are shared-tooling's (`web/eslint.config.js`, `web/stylelint.config.mjs`, `web/prettier.config.js`, the TypeScript configs, and `.golangci.yml`, generated from the template with `.golangci.local.yml` on top by `task shared:golangci:sync`). A rule turned off here says why, at the line it does not fit.
- The Vitest specs live in `web/src/__tests__/`, mirroring the source path, as `*.spec.ts`, on jsdom. The TypeScript configs are `tsconfig.app.json` (the app, without Node's types), `tsconfig.node.json` (the configs, `e2e/` and the scripts), `tsconfig.vitest.json` (the app's, then the shared base, taking in the specs) and a root `tsconfig.json` that only references them for editors.
- Coverage floors only rise: the front end's in `web/vite.config.ts`, the Go module's in `.github/workflows/ci.yml` and the Taskfile's `test:coverage`, the same number in both (sqlc's output left out of the count).
- The end-to-end suite runs against the real server built from the tree, on an empty library of its own; `e2e/a11y.e2e.ts` runs every main page through axe at WCAG 2.2 AA, so a new page goes on its list as well as `e2e/pages.e2e.ts`'s.

## Known traps

- The Go packages embed `web/dist`, so the front end builds before any Go build, test, lint or `go run` (`task` does it through `build:web`; CI's Go and generated jobs download the web job's build, and the end-to-end job builds it in its setup).
- A Go package ships inside one of the front end's npm packages (`web/node_modules/flatted`), so `go test ./...` here reaches it; golangci-lint skips it (`.golangci.local.yml`), and CI's Go job never installs node_modules.
- The text service writes the database too, so the deploy stops, starts and rolls back both services together; neither a migration nor a restore runs under it.
- The deploy's start check waits for `/healthz` on the host, and its smoke check needs this build's version from `/healthz` through Cloudflare; a version the ldflags don't set fails it.
- The end-to-end tests share one library and some depend on what another added, so they run in one worker, in order.
- The type checker reads TypeScript's narrowing across an `await` as final, so a flag a Stop button sets during the loop looks always false to `no-unnecessary-condition`; the two loops that check one say so at the line.
- `vite.config.ts` finds the pages a signed-out visitor sees by reading `public: true` beside `import('@/views/X.vue')` in `router/index.ts`, for the service worker's precache, so the two stay in one route object; the build fails when a public route matches no view, or a page only the owner sees gets into the precache.
- PrimeVue's icon style sits outside the cascade layers and loads after the app's, so an override of it (the spinners' reduced motion) can't live in a layer.
- The browser pane can't register a service worker; `e2e/offline.e2e.ts` checks it in Edge.
- sqlc reads `internal/db/schema.sql`, not the migrations (it cannot read a rebuild's temp tables), so after a new migration `task gen` writes the schema first; `TestSchema` fails until it does. Its type overrides match the declared type in capitals (`DATETIME`, `DATE`).

## Departures from the standards

- Backups: the nightly backup compresses the database, but the covers' and documents' files in each day's `files-YYYY-MM-DD/` stay as hard links to the live files, where the standard archives each folder as a daily `.tar.gz`. They take no room until the library lets a file go, and photographs and PDFs barely compress; a compressed copy would hold every file twice (deploy-and-ops.md, Backups).
- No restore drill is run on the host, by the owner's decision of 2026-11-15; the drill's steps stay in docs/ops.md for when one is wanted (deploy-and-ops.md, Restores).
- Icons: each component imports the definitions it uses and passes them to `:icon`, so there is no register in `src/fontawesome.ts` and no test of one; a missing icon fails the type check instead (components.md, Icons).
- Lists: the Stacks draw the library's books as spines on bookcases, a button each in a list a shelf, where the standard has every list of records in the one table: a table cannot draw a shelf, and the Books tab lists the same books as one (components.md, Lists and routes).
- Last passkey: `delete-passkey` removes the owner's last passkey, where the standard refuses it with 409. The owner is the one account and holds the host, where `homelibrary setup-code` makes a code that sets a device up again, so removing the last passkey (a lost phone's, say) locks nobody out for good (security.md, Sign-in and sessions).
- The text service's log level is `HL_LOG_LEVEL`'s until it restarts: it is a separate process with no API to change it through, and it logs a line for each file it reads (deploy-and-ops.md, Logs).

## Not yet meeting the standards

- Since 2026-11-15: `MemoryMax=` for both services is not yet from a peak that includes their heaviest work. The peaks measured that day (29 MiB and 7 MiB over 2.3 days) held no cover photo decoded and no document read, so the caps stay at 768M and 1G; waiting on the owner to use the site for a week after the 1.4.0 deploy, then on `Get-ServiceMemory` to set each cap to twice its peak (deploy-and-ops.md, Services and systemd).
